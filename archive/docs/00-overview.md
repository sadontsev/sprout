# Sprout — native Swift rewrite

A feature-for-feature reimplementation of the Expo/React Native app (`mobile/`) as a native
SwiftUI app (`native/`), so the two can be compared side by side.

The rule for this port is **lossless**: every behaviour the RN app has, the native app has. Where
the native platform allows something better, better is allowed. Worse is not.

## Layout

| Path | What |
|---|---|
| `native/project.yml` | The Xcode project, as data. `Sprout.xcodeproj` is generated by `xcodegen` and is gitignored — the same discipline `mobile/` uses for its `ios/` tree. |
| `native/Sprout/` | The app. |
| `native/SproutWidget/` | Live Activity widget extension (`com.example.sprout.LiveActivity`). |
| `native/Shared/` | Types compiled into both — chiefly `PrintActivityAttributes`. A mismatch here silently renders a blank Live Activity, so it must be one definition. |
| `native/SproutTests/` | Unit tests for the pure logic. |

## Build

```bash
cd native && xcodegen generate
```

Simulator (iOS 27 SDK, for verification against the target OS):

```bash
DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer xcodebuild -project native/Sprout.xcodeproj -scheme Sprout -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
```

Archive for TestFlight — **must** use the release Xcode; App Store Connect rejects beta-SDK builds:

```bash
DEVELOPER_DIR=/Applications/Xcode-26.3.0.app/Contents/Developer xcodebuild -project native/Sprout.xcodeproj -scheme Sprout -configuration Release -destination 'generic/platform=iOS' -archivePath /tmp/SproutNative.xcarchive archive
```

## Deliberate differences from the RN app

These are the only places the native build intentionally diverges. Everything else is a faithful
port.

| Area | RN | Native | Why |
|---|---|---|---|
| Theme | Mutable module-scope token object + `useSyncExternalStore` | `Palette` value in the SwiftUI environment | The environment already re-renders dependents; no mutation needed. Same 40 tokens, same two palettes. |
| `DashVM.stateColor` | A resolved colour string | A `StateColor` token resolved at render | The RN version had to rebuild the whole VM on theme change to avoid freezing the dark palette. Naming the token makes the VM genuinely theme-independent. |
| Number decoding | `asNum()` at every read site | `LooseNumber` in the `Decodable` conformance | The WebSocket stringifies numerics; handling it once at the boundary means no read site can forget. |
| Camera events | `(String, [String: Any])` | A `Sendable` `CameraEvent` enum | The payload crosses a queue hop, which strict concurrency cannot check on a dictionary of `Any`. |
| OTA updates | `expo-updates`, channel `production` | None | A native app ships through TestFlight. This removes the whole "applies on the second cold launch" class of confusion — and the `runtimeVersion`/`version` coupling that could orphan published updates. |
| Config storage | `expo-secure-store` | `Security.framework` directly | Same accessibility (`WhenUnlockedThisDeviceOnly`), same JSON blob. **The Keychain schema differs, so settings do not migrate — the base URL and API key must be re-entered once.** |

## The camera stream: fixed, and a warning about how it was misdiagnosed

Resolved 2026-08-10. The stream now runs at a steady **10 fps through the public host**, one connect,
zero reconnects. The cause was entirely client-side, and it was a single missing line.

### The bug

`MJPEGStreamClient.start(url:)` reset `parser` and `sawFirstFrame` but **not `demultiplexed`**.

That flag means "responses on this task are parts, not headers". Once set — which happens on any
connection URLSession chooses to de-multiplex — it survived into the next `start()`. So after the
first disconnect, every reconnect judged the opening `multipart/x-mixed-replace` response to be a
part, found it was not `image/*`, and rejected it as "camera unavailable" before a byte of video
arrived. The camera was permanently dead after one drop, with no path back short of relaunching.

The second-order damage was worse than the bug. Each failed attempt attaches a viewer server-side,
and the tight retry loop piled up **six subscribers and starved the camera for every client on the
network** — including plain `curl` from the server itself. The reconnect now falls back to a 20 s
cadence once a run of attempts has failed without a frame, so a client-side fault can never again
take the camera down for everything else.

### Two wrong conclusions, and why

Both were measurement errors, and both are worth remembering because they were confidently held:

1. **"Cloudflare buffers `multipart/x-mixed-replace`."** A `curl` through the public host returned 0
   bytes while the same request on `localhost` streamed fine — apparently decisive. But that test ran
   *during* the subscriber pile-up, i.e. the symptom was measuring the bug, not the transport. With
   the camera healthy, the public host streams ~27 MB in 12 s, plain, compressed or not, HTTP/1.1 or
   2. **The proxy was never involved.** No tunnel config change was needed or made.
2. **"Zero frames ever reached the renderer."** The frame counter appeared to read nothing, which
   pointed at the display layer. It was logging at `info` level, and `log show` drops `info` unless
   asked. The frames were there all along — 14.9/s.

The lesson for the next person: when a diagnostic contradicts a working control case, suspect the
diagnostic. And check the log level before concluding from silence.

## Known gaps — where the native build is NOT yet at parity

These are real feature losses against `mobile/`, not deliberate differences. Listed so the
"lossless" claim isn't quietly overstated.

| Gap | What's missing | What exists already |
|---|---|---|
| **Model texturizer** | `TexturizeClient` and the whole texturize UI (sheet, preview/commit, mapping modes, amplitude/scale/refine). | Settings toggle, URL resolution and health-probe config are in place, so this is the client plus one overlay. |
| **Push notifications** | No `UNUserNotificationCenter` registration, so no device-token POST to Trellis and no print-finished / cooldown banners. Live Activity push tokens *are* registered. | `ConfigRules.resolvePushUrl` and the `serverPush` setting. |
| **App Group assets** | The brand nozzle glyph and plate thumbnail are never written to the App Group container, so lock-screen cards fall back to an SF Symbol instead of the glyph + model image. | The widget already reads `iconUri` / `modelUri` and falls back cleanly. |
| **SD-card layer viewer** | The layer viewer is reachable for library files but not for a sliced 3MF on the printer's SD card — the overlay case takes a `LibraryFile`, and an SD file is addressed by path. | `client.printerGcodePath(_:path:)` is already there. |
| **`presentNozzles`** | Ported as a file-private helper inside `AmsView` rather than a tested `Domain/` module, so it is the one piece of ported logic without tests. | The logic itself is complete, including the rack/no-rack cross-map. |

## Acceptance criteria

Status as of build 7 (2026-08-10).

**What could be verified without credentials, and was:** the app builds against the iOS 27 SDK, runs
on an iOS 27 simulator, launches without error, renders onboarding in both palettes, accepts its URL
scheme, and passes 488 unit tests covering every pure module — the state classifier, AMS topology,
LAN gating, colour handling, cooling, dryer, power, config rules, Live Activity content and change
gating, the WebSocket frame parser, and the MJPEG demuxer.

**What could not be, and why:** every criterion that needs a live printer needs the Bambuddy API key
typed into the app, and entering an API key is something to do yourself rather than have an agent do.
So the connected half of this list is **unverified** — marked ⏳ below. Enter the key once on the
TestFlight build and they become checkable in minutes.

Legend: ✅ verified · ⏳ needs the app connected to your Bambuddy · 📱 needs hardware, not a simulator.

One honest caveat on the ✅ marks in sections B, C and E: those are verified **as logic**, by tests
that feed the real payload shapes through the same functions the views read. That is the layer where
every one of these has historically broken. It is not the same as having watched the pixels — the
rendering of that logic is still unconfirmed.
